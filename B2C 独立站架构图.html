B2C 独立站架构图

一套 B2C 独立站方案：Medusa v2 后端打成 Docker 镜像部署到海外高资源 VPS（VPS 上只跑应用容器）， 店面（Next.js，UI 用 shadcn/ui + Tailwind CSS）放 Vercel（当前不涉及商业使用，用免费 Hobby 计划即可），数据库用 Supabase 的托管 PostgreSQL、缓存与队列用 Upstash 的托管 Redis（都走免费额度），支付走 Stripe、邮件通知走 Resend，上传文件存 Cloudflare R2。下面五个视图分别是运行架构、构建部署链、版本更新流程、数据与备份和答疑——文件存储、备份恢复演练、日志轮转、站外监控、自动部署、staging 彩排这些运维做法都已经是这套架构的一部分；图里的方框可以点，点开看每个组件的说明。

镜像 = 代码 image

Medusa 程序本身打进镜像，版本由镜像标签决定，换版本就是换镜像。

数据库与缓存用托管，不自托管 Supabase · Upstash

数据库不打进 Medusa 镜像，也不在 VPS 上自己跑容器：PostgreSQL 放 Supabase、Redis 放 Upstash，都是托管服务、免费额度起步。VPS 上只跑 Medusa、Caddy、Worker 这些应用容器，不再维护数据库容器和数据卷，连接地址靠环境变量传入。

更新 = staging 彩排 + 自动部署 db:migrate

新版本先在 staging 环境跑一遍迁移、验证下单与后台，没问题再上生产；生产部署由 deploy.sh / GitHub Actions 自动串起备份 → 拉新镜像 → 一次性迁移 → 建默认管理员 → 启动服务。迁移脚本是框架代码的一部分，跟着代码一起打进镜像。

备份 = 定时导出 + 异地 + 演练 pg_dump

Supabase 免费版不带自动备份，所以更要自己来：定时对 Supabase 里的 PostgreSQL 远程跑 pg_dump 导出、打包，存进 Cloudflare R2 的备份 bucket：每天一份留 30 天、每月一份留 3 个月；每季度做一次恢复演练，没验证过的备份等于没备份。Upstash 的 Redis 丢了能重建，不用备份。

迁移靠流程，不靠人记 db:migrate

生产环境用受控的一次性迁移步骤：迁移跑完再启动服务，避免多容器抢迁移。本地 / 单容器才用 entrypoint 启动时自动检查，先跑 db:migrate 再起服务。迁移幂等，只跑没跑过的。

地址靠环境变量传 DATABASE_URL

数据库在哪不写死在镜像里：Medusa 启动时读 DATABASE_URL，里面是 Supabase 给的连接地址；REDIS_URL 同理指向 Upstash。同一个镜像换个变量就能连不同的库——生产和 staging 各用一个 Supabase 项目、一个 Upstash 数据库。

生产必需环境变量配齐 .env

上线前必须配齐：DATABASE_URL、REDIS_URL、JWT_SECRET、COOKIE_SECRET、STORE_CORS / ADMIN_CORS / AUTH_CORS、MEDUSA_BACKEND_URL、STRIPE_API_KEY、STRIPE_WEBHOOK_SECRET、RESEND_API_KEY。密钥只放服务器环境变量，不进镜像、不进仓库。

Admin 要知道后端在哪 admin.backendUrl

Admin 是静态页面，本身不知道后端地址：靠 admin.backendUrl（环境变量 MEDUSA_BACKEND_URL）指向后端公网地址，后台才调得到 API。同时把这个后端地址本身也加进 ADMIN_CORS / AUTH_CORS（连同后台访问域名一起），不然登录与跨域请求会被拦、后台打不开。

支付与通知接外部服务商 Stripe · Resend

空白版 Medusa 默认不能收款、不会发邮件：支付接 Stripe Module Provider 并在 Region 里启用，邮件通知接 Resend（免费额度），异步发送由 Worker 容器跑。

搜索：暂不接 search

搜索：暂不接，店面先不上搜索框。空白版 Medusa 默认不带搜索引擎，不要默认它有；以后要接再选 Meilisearch 或 Medusa Search，到时再补索引服务与店面搜索框。

上传文件存 R2，不落容器 @medusajs/medusa/file-s3

商品图片等上传文件经 @medusajs/medusa/file-s3 插件直接存进 Cloudflare R2 的文件 bucket，不存 Medusa 容器本地——容器随便重建、换机器，图片都不丢。生产环境的 file_url 要用绑在 R2 上的自定义域名，不要用 r2.dev 公开链接。

监控在站外，日志有上限 uptime · logging

站外监控（Uptime Kuma 放在另一台 VPS）每分钟检查首页与 /health，挂了立刻 Telegram / 邮件告警；Compose 给每个服务设日志轮转（max-size 10m × max-file 3）和内存上限，日志打满磁盘、单容器拖垮整机的事从源头堵住。

运行架构：顾客的一次访问怎么走

实线是顾客的请求路径，虚线是后台访问与外部服务调用。数据库在 Supabase、缓存与队列在 Upstash，都是托管服务、不在 VPS 上；上传文件走 Cloudflare R2、支付走 Stripe、通知走 Resend、异步任务由独立的 Worker 容器跑、站外监控独立在另一台 VPS 上盯着，都是这张图的一部分。点击任意方框看说明。

构建与部署：代码怎么变成 VPS 上跑着的服务

官方没有现成的 Medusa 镜像，所以镜像由你自己的 CI 打；部署也不靠人手动 SSH——push 后由 GitHub Actions 先把新版本部署到 staging，跑迁移、验证下单与后台，通过后才 SSH 到生产 VPS 执行 deploy.sh；staging 没通过，生产一步都不动。点击任意方框看说明。

版本更新流程：Medusa 发新版时你要做的事

这正是你想要的工作方式——日常更新不动服务器环境，只换镜像；而且先在 staging 彩排、再由脚本自动部署到生产，不靠人手动 SSH 一步步敲。

  1. 1
    看 release notes

    先确认这次更新有没有 breaking change。patch 只修 bug；minor 可能有 breaking change；major 是架构大改，要按官方升级指南走，必要时跑官方 codemods 自动改代码。

  2. 2
    升 npm 依赖

    把 package.json 里所有 @medusajs/* 包一起升到同一个新版本号（官方每次发版统一版本号，保证互相兼容），然后 npm install。

  3. 3
    提交并推送：先自动部署到 staging

    git push 到 main，GitHub Actions 自动打新镜像、推到 GHCR（镜像标签是这次的 commit 号），然后先把新版本部署到 staging——这一步生产环境完全不动，还跑着旧版本。

  4. 4
    在 staging 彩排验证（生产门禁）

    Staging 是和生产长得一模一样的彩排环境：在高资源 VPS 上再起一套同样的 Compose，换个子域名和端口；数据库不用在 VPS 上另起容器——新建一个独立的 Supabase 项目，把生产备份导入一份，Redis 用一个独立的 Upstash 数据库。新版本已经部署到 staging，在这里跑一遍迁移、点一遍下单和后台——验证通过，流水线才放行生产部署；没通过就停在这里修，生产保持旧版本，把翻车挡在顾客看到之前。嫌全套太重时，最低限度也要在 staging 把迁移跑通、验证数据不丢。

  5. 5
    staging 通过后，才自动部署到生产：先备份，再拉新镜像

    部署由 GitHub Actions 自动 SSH 到 VPS 执行 deploy.sh 一键完成，不再靠人手动敲——前提是上一步 staging 验证已经通过，没通过流程到此为止、生产保持旧版本。脚本第一步先对 Supabase 里的 PostgreSQL 远程跑一次 pg_dump 备份并存进 R2 备份 bucket——迁移出问题时能回得去，有些数据迁移是不可逆的；然后 docker compose pull 拉下新镜像，先别急着启动服务——下一步先跑迁移。数据库和缓存都在托管服务那边，不在这台 VPS 上，这一步不碰它们。

  6. 6
    跑数据库迁移 + 建默认管理员（生产：一次性步骤）

    deploy.sh 在启动服务之前，用一个受控的一次性步骤单独跑 npx medusa db:migrate（用新镜像起一个临时容器执行，跑完即退出），迁移确认完成后再启动 Server 和 Worker——这样避免多个服务同时启动时抢着迁移、互相冲突。它怎么知道跑哪些？先查数据库里的一张记录表（记着哪些迁移已执行），再对照镜像里带的迁移文件，只按顺序执行没跑过的——重复执行也不会重复建表。迁移跑完之后、启动服务之前，脚本紧接着用新镜像起一个临时容器跑 npx medusa user -e -p ，自动创建默认管理员（邮箱 、密码 ，首次登录后立即改密码）。这一步是幂等的：先查数据库里是否已有管理员，有就直接跳过——绝不能因为用户已存在就报错、让整个部署失败；所以首次部署时它把号建好，后续每次版本更新跑到这里都会自动跳过。这一步由部署脚本串行执行、靠流程保证，不靠人记。本地 / 单容器场景才用 entrypoint 自动检查：把 db:migrate 写进启动脚本，容器一启动先跑迁移再起服务，图省事。

  7. 7
    大版本升级单独处理

    跨大版本时迁移可能不只是加列改表，还会动数据格式、拆表。标准做法是先看官方升级指南：有时不能跳版本、要逐个版本升，有的版本要先跑 codemods 改代码。先在 staging 把整个升级跑通、验证完，备份确认好之后，生产仍走一次性迁移步骤、但要手动确认每一步——流程化替代不了这一步判断，本地的 entrypoint 自动检查更不能直接套到生产大版本升级上。

  8. 8
    首次部署清单（只在第一次上线时做）

    db:migrate 只建表，不会自动生成任何业务数据——首次部署还要按顺序把这三件事做完，店才真正能营业：建 Store / Region（含启用 Stripe）→ 建 Sales Channel → 生成 Publishable API Key 配给店面。Admin 用户不在这份手动清单里，它由部署脚本自动完成：deploy.sh 在一次性迁移跑完之后、启动服务之前，已经用新镜像起临时容器跑 npx medusa user -e -p 建好默认管理员（邮箱 、密码 ，首次登录后立即改密码），且幂等——数据库里已有管理员时自动跳过，不会因为用户已存在让部署失败。手动跑命令只是备用：Medusa 后台没有注册入口，只有登录页——数据库里 0 个用户时打开后台仍是登录页，万一自动创建没生效，才在后端容器里手动跑同一条 npx medusa user -e <email> -p <password> 补建。部署完成后用默认管理员登录后台，依次建 Store 和 Region（在 Region 里启用 Stripe 支付）、建 Sales Channel 并关联商品，最后生成 Publishable API Key 填到店面的环境变量里——店面没这个 Key 就调不到 Store API、商品页是空的。这份清单只在首次部署时走一遍，后续版本更新不用重复。

最容易漏的一步是迁移，所以它被写进了 deploy.sh 和 staging 彩排流程。只换镜像不迁库，新代码对不上旧表结构，服务会直接起不来；现在新版本先在 staging 把迁移跑通，生产部署时脚本在启动服务前自动执行一次性迁移步骤，靠流程保证、不靠人记；entrypoint 自动检查只留给本地 / 单容器。

数据与备份：数据库不打包，备份单独走一条线

架构里数据分四处安放：业务数据在 Supabase 的托管 PostgreSQL，缓存与队列在 Upstash 的托管 Redis，上传文件在 Cloudflare R2 的文件 bucket，数据库备份在 R2 的备份 bucket。VPS 上不跑任何数据库容器。备份的对象只有 PostgreSQL，且要定期做恢复演练。点击任意方框看说明。

先分清：数据库、缓存、文件，各放各的

PostgreSQL Supabase · 托管

  • 存商品、订单、用户、库存——丢了就是丢生意
  • 跑在 Supabase 的托管 PostgreSQL 上（免费版），不在 VPS 上起容器、不占本机磁盘
  • 必须备份：Supabase 免费版不带自动备份，靠自己定时 pg_dump 导出到 R2
  • 换 VPS 不用搬数据库：新机器改个 DATABASE_URL 指过去就行

Redis Upstash · 托管

  • 只做缓存、事件和队列，严格说不是业务数据库
  • 跑在 Upstash 的托管 Redis 上（免费版），不在 VPS 上起容器
  • 数据丢了能重建，所以不备份、不需要异地存放
  • 生产要配齐四个模块：Caching（缓存）、Event Bus（事件总线）、Workflow Engine（工作流引擎）、Locking（分布式锁），都通过 REDIS_URL 连同一个 Upstash 数据库

上传文件 Cloudflare R2 · 文件 bucket

  • 商品图片等上传文件经 @medusajs/medusa/file-s3 插件（S3 兼容 endpoint + bucket + API Token）直接存 R2
  • 生产环境的 file_url 要用自定义域名，不要用 r2.dev 公开链接
  • 不落 Medusa 容器本地：容器重建、换机器都不丢图片
  • 和备份 bucket 分开：一个管营业文件，一个管数据库备份；R2 每月 10GB 存储免费、出口流量免费

备份怎么做：四步

备份的对象只有 PostgreSQL。目标是：Supabase 账号或 VPS 任一边出事，也能把店恢复出来。

  1. 1
    定时远程导出

    用定时任务（比如每天一次）通过 Supabase 给的连接串连过去，对里面的 PostgreSQL 跑 pg_dump，导成一个 SQL 文件。这是逻辑备份，导出的文件干净、可移植。Supabase 免费版不提供自动备份（付费版才有），这条自备的线不能省。

  2. 2
    打包并带上日期

    把导出的 SQL 压缩打包，文件名带日期（如 backup-2026-11-20.sql.gz）。保留策略固定下来：每天一份留 30 天、每月一份留 3 个月，超期的自动清理——既不只留最新一份，也不会无限堆积。

  3. 3
    存进 R2 备份 bucket

    把备份包传出这台 VPS，存进 Cloudflare R2 的备份 bucket（和文件 bucket 分开）。只存在本机不算备份——VPS 挂了会跟着一起没；放 R2 既是异地，成本又低。

  4. 4
    定期做恢复演练

    有备份不等于能恢复：上线前先做一次完整演练——新建一个临时 Supabase 项目（或临时 PostgreSQL），把最新备份导入，确认能起来、商品和订单都在；之后每季度抽查一次。真要恢复时照同一套走：把备份导入一个新的 Supabase 项目、改 DATABASE_URL 指向新库、跑 db:migrate 对齐表结构、打开店面确认。没演练过的备份等于没备份。

别指望 Supabase 免费版自带备份。自动备份是 Supabase 付费版的功能，免费版没有——所以 pg_dump 导出到 R2 这条线必须自己搭、不能省；哪天升级到付费版，也建议保留这条线，手里多一份自己掌控的异地副本。另外免费项目长期没有任何活动会被 Supabase 暂停，生产店有正常流量一般不会触发，staging 项目长时间不用时记得先唤醒再部署。
R2 里两个 bucket 别混：文件 bucket 存正在营业用的商品图片，Medusa 运行时天天读写；备份 bucket 只存 pg_dump 的历史备份包，平时只进不出。分开之后，清理旧备份不会误删商品图，恢复演练也不会碰到线上文件。

答疑：架构、迁移与外部服务的常见问题

这部分按通用架构整理，不绑定某个具体项目：问题已改写为通用问法，答案是讨论后定下来的结论，标准做法也已同步写进前面的视图。Resend 部分只保留可复用的验证经验；DNS 记录、配额、控制台界面和账号策略以当前账户页面为准，不把一次实测当成所有账户的通用保证。

Q数据库要不要跟代码一起打进镜像？

不打进镜像，也不在 VPS 上自托管，用托管服务。镜像是代码，容器随时可以删掉重建——数据放进镜像，容器一删数据就没了，数据一变还得重打镜像。这是 Docker 的基本规矩：数据不进镜像。

这套架构更进一步：PostgreSQL 放 Supabase、Redis 放 Upstash，都是服务商托管的，数据根本不在这台 VPS 上。换镜像、重建容器、甚至换一台 VPS，数据都不受影响，新机器改个连接串就行。唯一要另外补的是备份：Supabase 免费版不带自动备份，要自己定时 pg_dump 到 R2（见「数据与备份」视图）。

Q数据库、缓存、文件分开放，再加定时备份——这套分工对不对？

对，各管一摊。一：分工不同——PostgreSQL（Supabase）是真正存数据的数据库；Redis（Upstash）是缓存和队列，严格说不算数据库，数据丢了能重建，所以叫「一个数据库 + 一个缓存」更准确；上传文件是第三摊，放 R2。二：数据库和缓存都用托管服务，省掉自己维护容器、数据卷和版本升级，免费额度对起步阶段基本够用。三：托管不等于不用备份——Supabase 免费版没有自动备份，稳妥做法仍是定时 pg_dump 导成 SQL 打包存到 R2，异地且在自己手里。Redis 不用备份。

Q大版本对不上时，迁移到底改的是哪一边的结构？

两个都不是。先纠正一个关键点：镜像里没有数据库，只有 Medusa 的程序代码和跟着代码版本走的迁移脚本；数据库在 Supabase 的托管 PostgreSQL 里，和镜像、和 VPS 都是分开的。跑迁移的过程是：拉新镜像 → 先用新镜像起一个一次性迁移容器、只跑迁移命令（不启动服务）→ 迁移程序先查数据库里一张记录表（记着哪些迁移已执行过）→ 按顺序执行没跑过的脚本，直接对 Supabase 的 PostgreSQL 发 ALTER TABLE、CREATE TABLE，把表结构改成新版需要的样子 → 迁移确认完成，再启动新的服务容器。所以不是你手动改数据库文件，也不是改镜像里的结构，而是新镜像带的迁移脚本去改 Supabase 里数据库的表结构，你只需要下「跑迁移」这个指令。

大版本对不上时，迁移可能不只是加列改表，还会动数据格式、拆表：按官方升级指南走，有时不能跳版本、要逐个版本升，有的版本要先跑 codemods 改代码。还有：跑迁移之前先备份——db:rollback 能回滚结构迁移，但有些数据迁移不可逆，这步不能省。

Q数据库在服务商那、程序在镜像里，程序怎么改到数据库的结构？

关键一点：镜像启动后就是个活的程序，不是密封的盒子。新镜像启动成容器，Medusa 程序跑起来，按 DATABASE_URL 通过公网加密连接连上 Supabase 的 PostgreSQL——和你在电脑上用数据库工具连上去是一回事，都是通过网络发 SQL；它把迁移脚本一条条发过去，PostgreSQL 执行完，表结构就变了。

所以镜像自己不改数据库，是镜像启动后跑起来的程序去改的。「镜像只读」指镜像自身的文件不能改，程序通过网络改数据库完全不受影响，因为数据库根本不在镜像里，在 Supabase 那边。前提只是 DATABASE_URL 配对：里面是 Supabase 的连接地址，程序通过公网 TLS 连过去发 SQL。

Q数据库不在 VPS 上，数据到底存在哪？迁移脚本是框架自带的吗，会随镜像一起打包吗？

数据存在服务商那边。业务数据在 Supabase 的托管 PostgreSQL 里，缓存和队列数据在 Upstash 的托管 Redis 里，都是服务商的机器在存、在维护。VPS 上只有 Medusa、Caddy、Worker 这些应用容器，本身不存业务数据——容器删了重建、甚至整台 VPS 换掉，数据都不受影响，新机器把连接串配上就能继续营业。

迁移脚本就是 Medusa 框架代码的一部分，每个模块（商品、购物车、订单等）都自带自己的迁移文件，打镜像时跟着代码一起打进去。链条是通的：代码更新 → 新镜像里有了新迁移脚本 → 跑迁移（连上 Supabase 执行）→ 数据库结构跟着变。迁移脚本跟着代码走，数据在托管服务里，两边分开，各走各的。

Q新镜像怎么知道数据库在哪，又怎么决定要执行哪些迁移？

这是两个不同的「怎么知道」。数据库在哪——靠环境变量，不是写死在镜像里：Medusa 启动时读 DATABASE_URL（格式 postgres://用户名:密码@主机:端口/库名），这个变量在启动容器时传进去，里面填的是 Supabase 项目给的连接地址（走它的连接池），同一个镜像换个变量就能连不同的库（开发、staging、生产各一个 Supabase 项目）；REDIS_URL 同理，填 Upstash 给的连接地址。

什么时候执行——靠命令触发，官方标准命令是 npx medusa db:migrate，在容器里执行即可；生产把它做成部署流程里的一次性独立步骤，本地也可以写进启动脚本自动跑（见下一条）。跑哪些——程序自己判断：连上数据库先查记录表，再对照镜像里的迁移文件，把没跑过的按顺序执行。总结：地址靠环境变量传进去，执行靠命令触发，跑哪些靠程序比对记录表自己决定。

Q迁移应该在什么时候执行，生产和本地的做法一样吗？

不一样，按环境分。生产环境用受控的一次性迁移步骤：部署时单独跑一次 db:migrate，迁移完成后再启动 Server 和 Worker。好处是时序可控、不会多容器抢迁移，出问题也能在服务对外之前拦住。本地 / 单容器才用 entrypoint 自动检查：把 db:migrate 写进启动脚本，容器一启动先跑迁移再起服务，图省事——单容器不存在抢迁移的问题，这样最方便。

共同点是都不靠人记：生产靠自动部署脚本（deploy.sh / GitHub Actions）里固定的一步保证，本地靠 entrypoint 保证；迁移本身是幂等的，只跑没跑过的，重复执行也不会重复建表。大版本升级仍要先看官方升级指南、备份好，先在 staging 跑通再走生产的一次性步骤并手动确认。核心一句话：迁移这步不要靠人记，要靠流程保证；生产用一次性步骤，本地才用自动检查。

Q迁移脚本在镜像里，怎么做到迁移跑完再启动服务？

关键是分清：启动容器不等于启动服务。镜像只是一个打包好的程序集合，里面可以有多条命令；容器只是运行环境，启动容器时让它跑哪条命令，它就只做哪件事。同一个镜像可以跑出两种完全不同的进程：一次性的迁移进程，和常驻的服务进程。

镜像自带一个默认命令，一般就是启动服务。不带命令启动容器，跑的就是默认命令：docker run 新镜像 等于直接起服务。带上命令，就是临时改跑指定的那一条，默认命令这次不执行：docker run --rm 新镜像 npx medusa db:migrate 只跑迁移，连上数据库、执行完未跑过的脚本就退出，根本不会启动 HTTP 服务；随后再 docker run -d 新镜像 起常驻的服务容器。

所以生产的一次性迁移步骤就是这么实现的：同一个镜像，先起一个临时容器只跑迁移命令，跑完自动退出；确认迁移完成，再起服务容器跑默认命令。两次用的镜像、网络和 DATABASE_URL 等环境变量完全一样，区别只在「这次让它干什么活」——平时起服务不用带命令，只有跑迁移那一次才需要带命令临时改跑。

QResend 域名验证怎么做，为什么 DNS 记录加了还是发不了？

未验证域名不能当生产发信方案；先验证专用发信子域名，再让发件人地址与已验证子域名完全匹配。在本次验证中，未验证域名只能使用 onboarding@resend.dev 作为沙箱发件人，收件人也受注册邮箱限制；要给真实顾客发送订单、发货或密码邮件，必须先验证自己的域名或子域名。实际验证经验是：用 mail.example.com 这类子域名比直接动根域名更稳，也便于把事务邮件和营销邮件隔离。不要用 send.example.com 作为验证子域名——Resend 默认会把 Return-Path 放在 send 子域名下，容易变成重复的 send.send.example.com；也不要复用已有其他记录的子域名，因为同名 CNAME 不能和其他记录共存。

2026 年 8 月后新建的域名通常会看到 send.mail 与 rsend.mail 两条 CNAME；本次还列出了 resend._domainkey.mail 的 DKIM TXT（具体公钥值只从控制台复制），页面还可能同时列出其他记录；控制台列出的每一条都要添加，少一条 CNAME 就可能停在 partially_verified。较老账号可能仍是 MX + TXT（含 SPF / DKIM）形式，记录的主机和值各账号不同，必须以 Resend 控制台当前显示的为准，不要照抄教程里的固定值。

如果 DNS 托管在 Cloudflare，Resend 相关 CNAME 要设为“仅 DNS”（灰云），不能开橙云代理，否则校验读到的是 Cloudflare 的地址；主机记录也不要重复填写域名后缀。加完记录后在 Resend 点 I've already added the records 触发校验；刚开始显示 Pending 很正常，等待 DNS 传播后再复查，这次实际验证约两分钟后变为 Verified / Forge Ready。如果 Resend 或 Cloudflare 登录触发异常或 Turnstile，按项目约束使用用户授权的本地 Chrome 完成操作，不依赖云端浏览器。

发件人必须从已验证的子域名发：验证 mail.example.com 后可以使用 noreply@mail.example.com、orders@mail.example.com 等任意前缀，但不能改成根域名地址，否则会报 403 domain mismatch。前缀默认只能发不能收；要接收顾客回复，还要在域名服务商配置 Email Routing。DMARC 建议先在根域名的 _dmarc TXT 使用 p=none 观察报告，确认 SPF / DKIM 对齐后再收紧策略；只加在发信子域名下的 DMARC 只覆盖该子域名。

本次验证结论：域名侧已经完成验证并开启发送；当前工作区的真实邮件链路仍需把运行时 RESEND_FROM_EMAIL 指向已验证子域名上的地址，再按项目测试流程发送真实测试邮件。不要把 API Key、完整 DKIM 公钥或控制台项目链接写入架构图。
